# 知序 · 个人事务操作系统

> 知其所想，序其所行。

知序把「想做啥」「什么时候能做」「必须先做哪个」放进同一条时间线，自动排出**什么时间做什么事**。

它不是待办清单——清单只负责记住，知序负责**安排**。

---

## 一、一句话说清

一个人同一时间只能做一件事。给三份输入，得一份输出：

- **输入**：任务（做什么、多久、最晚哪天）、依赖（谁先谁后）、可用时间（一周里哪些时段能干活）
- **输出**：每个任务的具体开始和结束时间

---

## 二、排期怎么运转

算法在 `src/scheduler/index.ts`，是**纯函数**：同样的输入永远得出同样的结果，不碰数据库，没有随机性。所以每次算出的排期都可复现、可验证。

它按四步走：

**第 1 步 · 理清先后（拓扑排序）**
按依赖排出合法顺序。A 等 B、B 又等 A 这种死循环，直接报错，绝不硬排。
同时可做的任务，截止日期近的优先，其次工期短的优先。

**第 2 步 · 确定最早能开始的时刻**
从下面几项里取**最晚的那个**：当前时间、最早开始日期、依赖推导出的时刻、已完成任务占住的时间段。

**第 3 步 · 在可用时间里找空位**
可用时间按星期重复（如"每周二 09:00–17:30 工作"）。找空位时：

1. **类别优先**：工作任务先找"工作"专属时段，找不到才用"不限"时段
2. **不跨块**：一个任务必须完整落在一个连续时段里，不拆成两半
3. **先完整后压缩**：放不下就把工期压到"单次最短安排"，塞得进就塞（标记「已压缩」）
4. **还放不下才顺延**：换下一个可用时段，或下一天

**第 4 步 · 互不重叠**
已排出的时段记成"占用表"，后面的任务必须避开。一个人同一时刻只能做一件事，这条是硬的。

### 四种依赖

都可以再加延后天数（lag）：

| 类型 | 含义 | 后继最早开始 |
| --- | --- | --- |
| **FS** 完成-开始 | 前者做完，后者才能动 | 前者结束 + lag |
| **SS** 开始-开始 | 前者一动，后者也能动 | 前者开始 + lag |
| **FF** 完成-完成 | 两者一起收尾 | 前者结束 + lag − 后者工期 |
| **SF** 开始-完成 | 前者一动，后者该收尾 | 前者开始 + lag − 后者工期 |

> 单线程下，SS 和 SF 排出来的时间常和 FS 接近——位置被占住了，想并行也并行不了。

## 三、系统怎么搭的

三层，边界清楚：

```
界面  src/ui + App.tsx        ← 衣服：随便换
  │ 只通过 repository.ts 取数
大脑  src/scheduler/index.ts  ← 骨架：换它系统就变另一个东西
  │ HTTP 接口 /api/*
身体  server/index.js + app.db ← 数据：衣服换了、骨架调了，数据一条不少
```

**界面像衣服**：换配色、换布局、甚至做成手机原生 App，只动第一层。后端不认识 React，只认 JSON。

**算法像骨架**：改样式不动它；但要把"按截止日期排"改成"按精力排"，那是换骨架。

**唯一要两边一起改的地方**：前端 `types/index.ts` 与数据库表字段必须对齐。加字段两边都要写。这是前后端分离的固定成本，换来两边各自独立演进。

## 四、技术栈

| 层 | 用了什么 | 为什么 |
| --- | --- | --- |
| 前端 | React 19 + TypeScript | 组件化；类型检查挡住大量低级错误 |
| 构建 | Vite 8 | 启动快、热更新快 |
| 样式 | Tailwind CSS 4 | 改样式就在标签上改，不用维护一堆 CSS 文件 |
| 后端 | Node.js 原生 HTTP | 不引框架，300 行搞定，依赖越少越稳 |
| 数据库 | SQLite（Node 内置） | 一个文件就是全部数据，备份就是复制文件 |
| 运行 | systemd 用户服务 | 开机自启，崩了自动拉起 |
| 远程 | Tailscale | 手机在外也能打开，不暴露到公网 |

### 数据表结构

六张表，全部存在一个 SQLite 文件里。前三张在用，后三张是预留给以后扩展的。

**`tasks` · 任务**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 文本，主键 | 唯一编号 |
| `title` | 文本，必填 | 任务名 |
| `parentId` | 文本 | 父任务编号；为空表示顶级任务 |
| `estimatedHours` | 数字 | 预计耗时（小时） |
| `minHours` | 数字 | 单次最短安排；时间块放不下完整工期时压到这个时长 |
| `startDate` | 日期文本 | 最早开始日期，这天之前不排 |
| `deadline` | 日期文本 | 截止日期，空表示没有硬期限 |
| `actualHours` | 数字 | 实际耗时，完成时填 |
| `isCompleted` | 0 / 1 | 是否已完成 |
| `scheduledStartAt` | 时间文本 | 完成时锁定的排期开始时刻，用来还原真实时间线 |
| `completionNote` | 文本 | 完成结果 / 复盘备注 |
| `category` | 文本 | `work` 工作 / `personal` 生活 / `any` 不限 |

**`dependencies` · 任务依赖**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 文本，主键 | 唯一编号 |
| `fromTaskId` | 文本 | 前置任务 |
| `toTaskId` | 文本 | 后继任务 |
| `type` | 文本 | `fs` / `ss` / `ff` / `sf` 四种依赖 |
| `lagDays` | 数字 | 延后天数，可为 0 |

**`availabilityTemplates` · 每周可用时间**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 文本，主键 | 唯一编号 |
| `weekday` | 数字 0–6 | 0 是周一，6 是周日 |
| `startTime` | 文本 | 开始时间，如 `09:00` |
| `endTime` | 文本 | 结束时间，如 `17:30` |
| `category` | 文本 | 这个时段属于工作 / 生活 / 不限 |

**预留表**

| 表 | 打算装什么 | 状态 |
| --- | --- | --- |
| `scheduleEntries` | 每次算出的排期记录（taskId + 起止时间） | 表建好，暂不写入——排期只在内存里算 |
| `taskTemplates` | 常用任务模板，一键套用 | 表建好，未使用 |
| `taskFiles` | 任务附件（文件名、类型、大小、存放路径） | 表建好，上传功能未做 |

> 时间统一按 `Asia/Shanghai` 计算，存库时用 ISO 格式（如 `2026-10-21T01:00:00.000Z`），日期用 `YYYY-MM-DD`。

## 五、现有功能

- **任务**：增删改；字段含预计耗时、单次最短安排、最早开始日期、截止日期、类别；支持父子任务，父任务工期/时间由子任务汇总
- **完成复盘**：勾选时弹窗填写实际耗时和复盘备注；已完成任务沉入底部折叠区，📄 图标提示有笔记
- **依赖**：四种类型 + 延后天数；删任务是同一事务里清依赖、解开子任务
- **可用时间**：按星期配置，分工作/生活/不限，支持批量选天与复制
- **排期**：数据一变立刻重算，压缩模式、超期标记、已完成硬避让
- **其他**：深浅色主题、响应式布局、一键导出 JSON 备份

尚未实现：排期结果落库、账号体系、附件上传。

## 六、启动

```bash
npm install
npm run build
node server/index.js        # 默认 5190 端口
```

开发模式：`npm run dev`（前端热更新）+ 另开终端 `node server/index.js`。

生产运行已注册为 systemd 用户服务：

```bash
systemctl --user status task-scheduler
systemctl --user restart task-scheduler
```

数据库文件 `data/app.db`，备份时连同 `-wal`、`-shm` 一起复制。

## 七、版本号规则

界面左上角版本号与本文档同步，格式 `v主版本.次版本.修订号`：

| 位 | 什么时候加 |
| --- | --- |
| **主版本** | 产品形态变了，老用户的使用方式要改（如 v2 → v3 换后端存储） |
| **次版本** | 有新功能，老功能照旧能用（如 v2.1 → v2.2 加编辑） |
| **修订号** | 只修 bug、调样式、改文案 |

判断口径：**新增能做的事 → 次版本；只让原来的事做对 → 修订号。**

**每次改动必须同时完成三件事**，缺一不可：

1. 按规则判断该升主版本、次版本还是修订号
2. 更新界面左上角的 `APP_VERSION`
3. 在 `CHANGELOG.md` 写一条记录，说明改了什么、为什么改

每次改版在 `screenshots/` 留一张截图。
